# 派发器 M1 · 使用说明

> 版本：v0.6.0 配套 · 仅标准库 · 复用 `服务.py`，不改 `服务.py` / `web/` / 台账结构
> 设计规范见本文档各节；实现位于 `派发器.py`。

## 1. 它做什么

独立进程扫描台账里 `status='待处理'` 的工单，原子领取后调用 `服务.dispatch_chat()` 派给执行端，按中文错误短语黑名单判定成败，把回件、事件、状态、告警写回同一张台账。**零新增表、零结构改动**，所有派生数据从 `events` / `chat_messages` / `meta` 计算。

- 告警直调 `服务.notify_boss()`（写 `group_messages`），**不调 HTTP**（本地 API 需 `X-Deck-Token`，独立进程必 403）。
- 熔断**不写** `projects.status`，只写 `breaker` 事件 + 告警 + 跳单。
- 派发器**永不写人工签收态**；该状态只由主理人经 `/signoff` 写入。

## 2. 启动（3 条常用命令）

```bash
cd /d <仓库目录>

python 派发器.py --dry-run                          # 先看候选与取舍原因；不写表/事件/告警/心跳/锁（仍写日志）
python 派发器.py --once --allow-real-db             # 操真实台账跑一轮（显式开关）
python 派发器.py --loop --allow-real-db             # 常驻，每 interval_s 一轮
```

其它：

```bash
python 派发器.py --once --allow-real-db --project proj-xxx
python 派发器.py --once --allow-real-db --ticket WO-DB-CX-9c1b3d5e
python 派发器.py --db 测试.sqlite3 --config 测试配置.json --data-dir 临时数据目录
python 派发器.py --init-db --db 测试.sqlite3         # 仅临时库建表/种演示数据
```

### CLI 参数

| 参数 | 说明 |
|---|---|
| `--once` | 跑一轮，等本轮所有 worker 收完再退出（默认行为） |
| `--loop` | 按 `interval_s` 循环；每轮开始写心跳 |
| `--dry-run` | 只打印候选及取舍原因；不 claim、**不写表 / 事件 / 告警 / 心跳 / 锁**，但 `RotatingFileHandler` 初始化时仍会创建并追加 `数据/派发器.log`（R2：只读是指台账，不是零文件写入）。预检额外报「执行端未就绪」「pull 型不支持同步收件」「人工席位，不派」「项目目录不存在」，只读调 `adapter_status()` / `SELECT projects.dir` |
| `--project` / `--ticket` | 限定范围，自检与人工重跑用 |
| `--db` / `--config` | 覆盖 `服务.DB_PATH` / `服务.CONFIG_PATH`，必须在任何读写之前生效 |
| `--data-dir` | 覆盖日志与 pid/lock 目录（自检隔离用；真实运行不要传，急停端点读的是默认 `数据/派发器.pid`） |
| `--allow-real-db` | 未传 `--db` 即视为真实台账，必须显式给本开关，否则退出码 4 |
| `--init-db` | 调用 `服务.init_db()`；**必须同时给 `--db`**，否则拒绝 |

### 退出码

| 码 | 含义 |
|---|---|
| 0 | 正常结束 / `dispatcher.enabled=false` |
| 2 | 已有派发器在跑（pid 存活），第二个进程不 claim 任何单 |
| 3 | 台账缺 `tickets` 表，拒绝隐式建表 |
| 4 | 真实库保护阀拦截，或 `--init-db` 未带 `--db` |

## 3. 停止

1. **优雅停止**：Ctrl+C / `SIGTERM` / `SIGBREAK` → 置停止标志 → 不再领新单 → 等当前 worker（最多 `dispatch_timeout_s`）→ 删 pid/lock → 退出码 0。
2. **UI 急停**：`/api/emergency-stop` 读 `数据/派发器.pid` 并 `taskkill /T /F`（Windows 硬杀，handler 不执行属预期）。硬杀残留的 `派发中` 单靠 **claim 超时回收**处理（D5，不改 `服务.py`）。
3. **锁残留**：pid 已不存活 → 下一进程打印 warn 并接管；也可手工删 `数据/派发器.pid` 与 `数据/派发器.lock`。

## 4. 配置（`配置.json` 的 `dispatcher` 段）

缺省也能跑，代码内全部有默认值。`max_retries` 仅兼容保留，**以 `max_attempts_per_ticket` 为准**。

| 键 | 默认 | 说明 |
|---|---|---|
| `enabled` | true | false → 启动即打印「派发器已关闭」退出 0 |
| `interval_s` | 5 | `--loop` 轮间隔；心跳超过 2× 视为卡死 |
| `max_concurrent` | 2 | 全局并发，领取只在主线程串行 |
| `max_concurrent_per_project` | 1 | 同项目运行中计数拦截 |
| `max_attempts_per_ticket` | 3 | 首次 + 2 次重试，任何路径都有上限 |
| `retry_backoff_s` | 10 | 指数退避基数：10 / 20 / 40… |
| `claim_timeout_s` | 600 | 超时领取回收阈值 |
| `dispatch_timeout_s` | 600 | 派发前对目标适配器浅拷贝覆盖 `timeout_s`，只改内存，不 `save_config` |
| `ticket_deadline_s` | 3600 | 按 `created_at` 算单张时限 |
| `no_progress_repeat` | 2 | 最近 N 条失败摘要相同即停 |
| `breaker_consecutive_fail` | 3 | 窗口内不同单号失败数阈值 |
| `breaker_window_s` | 300 | 熔断窗口，同时用于告警去重 |

## 5. 状态机

```
待处理 --claim(原子条件 UPDATE, rowcount 判定)--> 派发中
派发中 --成功, gate∈{None,'','无','-'}--> 已回件   next_action='已回件，无门禁'
派发中 --成功, gate 其他----------------------> 待验     next_action='<gate> 待评审，等待主理人签收' + 告警
派发中 --失败, attempts<上限------------------> 待处理   dispatch_fail + 指数退避，未到点本轮不领
待处理 --达到上限----------------------------> 失败     next_action='重试已用尽，等待人工处理'
派发中/待处理 --无进展----------------------> 失败     next_action='无进展：连续相同错误，等待人工复核'
派发中 --claim 超时且本进程未持有-----------> 待处理   claim_recovered，回收当轮不重领
待验   --主理人 /signoff-------------------> 人工签收态（派发器永不写）
```

前置条件硬失败（`projects.dir` 不存在、适配器未就绪、`pull` 型）走 **claim 后终态失败**，不静默跳过、不假装成功，避免永远不出队。

## 6. 事件链与落库

| 时机 | 事件（actor 一律 `派发器`） | detail |
|---|---|---|
| claim 成功 | `dispatch_intent` | `派发器领取：<执行端> 第 N 次` |
| 调用 `dispatch_chat` 之前 | `dispatch_ok` | `已投递：<label>` |
| 收到回件 | `reply_seen` | `首行前 120 字 \| 共 N 字，已写入 ticket:<id>` |
| 失败 | `dispatch_fail` | `attempt=N/M \| <错误短语 80 字>` |
| 治理 | `loop_guard_tripped` | `reason=attempts_exhausted / no_progress_same_error / no_progress_same_reply / deadline_exceeded` |
| 熔断 / 回收 | `breaker` / `claim_recovered` | 摘要 |

成功时同一事务写：`tickets.status/next_action/updated_at` + `chat_messages`（`conversation_id='ticket:<id>'`，`role='assistant'`，`project_id` 列存在才写，绝不自行 ALTER）+ `reply_seen`。`events.detail` 一律 ≤300 字并 `sanitize`；回件全文只进 `chat_messages`。

## 7. 判重与治理

- `canonical_sha256` 是 16–64 位十六进制才认；`manual`/`demo`/空走 `(project_id, executor, title)` 弱判重，且 `已回件`/`待验` 不参与弱判重。
- 失败判定**不用「以 `【` 开头」**：空回件 → `【大BOSS】` 前缀 → 中文错误短语黑名单 → 其余成功（`demo_chat` 的 `【演示回复 · 工单调度台】` 判成功）。
- 熔断：窗口内该项目**不同单号** `dispatch_fail(actor=派发器)` 达阈值且窗口内 `reply_seen` 为 0 → 写 `breaker` + 直调告警 + 不再入候选；`meta['breaker_notified:<pid>']` 去重；窗口条件不再成立即自动解除，无需清除操作。**不要用 `dispatch_ok` 当成功判据**——它只表示「已投递」。
- 脱敏：`sk-*`、`Bearer *`、`CODEBUDDY_API_KEY=*`、`api_key=*` 经 `服务.sanitize()` 后才入库/入日志；日志不 dump 整份配置。

## 8. 日志

`数据/派发器.log`，`RotatingFileHandler(5MB, backup=5, utf-8)` + 控制台，格式：

```
时间 | 级别 | 单号 | 事件 | 摘要
```

`meta.dispatcher_last_beat` 每轮（含每轮开始、`--once`）更新；外部判定超过 `2×interval_s` 未更新即卡死。`--dry-run` 不写心跳 / 锁 / 任何表，但**日志照常写**：`setup_logging()` 在进程启动阶段就创建 `数据/派发器.log`，即使 dry-run 也会留下文件（可用 `--data-dir` 指到临时目录做隔离）。

## 9. 排障

| 现象 | 排查 |
|---|---|
| 退出码 4 | 未传 `--db` 且未传 `--allow-real-db`；先跑 `--dry-run` |
| 退出码 2 | 已有实例；核 `数据/派发器.pid` 是否存活，残留可删 |
| 退出码 3 | `--db` 指到了空文件；用 `--init-db --db <临时库>` 建表，真实库绝不建表 |
| 单一直不派 | `--dry-run` 看跳过原因：项目暂停/停止、熔断中、未指定执行端、人工席位、执行端未就绪、pull 型、项目目录不存在、读不到适配器状态、退避未到点、判重、超时 |
| 单反复失败 | 看 `dispatch_fail.detail` 是否恒定 → 无进展保护会提前置失败 |
| dry-run 报「项目目录不存在」 | 只在 `projects.dir` 非空且路径不是目录时报；真跑会 claim 后判失败并告警（`next_action='项目目录不存在，等待人工'`）。`dir` 为空按 §7.6 回落 `cfg.paths.project`，不算错 |
| dry-run 报「读不到适配器状态」 | `adapter_status()` 抛异常时头部会打印一次原因，逐单不再伪装成「执行端未就绪」；先修配置/适配器文件 |
| dry-run 报「执行端未就绪」 | 真跑会 claim 后判失败并告警；先查 `enabled` / `adapter_status.ready` / `executor` 是否填了显示名 |
| 适配器未就绪 | `adapter_status(cfg).ready`：process 型需 `command[0]` 真实存在且已启用；名字进白名单不等于可执行 |
| pull 型 | 不支持同步收件，claim 后判失败，不假装成功；dry-run 会提前报「pull 型不支持同步收件」 |
| 急停后单卡在 `派发中` | 等 `claim_timeout_s` 自动回收；回收轮当轮不重领，下一轮再派 |

## 10. 已知边界

- 无进展的「回件 hash 相同」分支代码已实现，但 M1 失败路径不写回件文本，事实上不触发；M2 结构化返回后生效。
- 熔断状态完全由窗口派生、不持久化；项目状态仍由人工在 UI 上暂停/继续。
- 真实库从不被 `init_db()` 触碰；自检只用临时库并断言真实台账 `SHA256` + `mtime` 前后不变。
- 自检脚本给每个子进程注入 `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8`，并把自身 stdout 重配为 UTF-8，**在 Windows 默认 GBK 控制台下也能直接跑**，无需手工设环境变量；否则 `dry_reason()` 读不到中文 skip 原因会误判成等待超时。**这是自检夹具行为，不等于生产默认控制台编码被覆盖（R4）**：`服务.py` 的 process 适配器本就按 `encoding="utf-8"` 解码，落库不受控制台影响；豆包另以 `PYTHONIOENCODING=gbk` 且不设 `PYTHONUTF8` 对抗跑，19/19 通过。「自检绿」只证明用例与实现自洽，不替代生产环境联调。
- 回滚见 `改动说明_派发器M1.md`。

## 11. 复核后补充约定（M1 当前行为，务必先读）

1. **`--once` 不会重试**：一轮跑完即退出，退避未到点的单原样留在 `待处理`，本进程不会自动再领。要连续重试请用 `--loop`，或间隔足够时间后**再跑一次** `--once`。自检的重试驱动也是「等实现判可派 → 再跑一轮」，不靠固定 `sleep` 猜退避（`retry_backoff_s * 2**(n-1)`，默认 10s→20s→40s）。
2. **`recover_claims()` 不按 `--project` / `--ticket` 过滤**：带 `--project A` 运行时，会顺手回收 B 项目超时卡住的 `派发中` 单（写 `claim_recovered`）。无害但属意外副作用；M1 保持现状，M2 建议加范围过滤。真跑前若有跨项目手工卡单，请注意这一点。
3. **告警范围（M1 现状）**：进入终态失败（重试用尽 / 无进展 / 前置条件硬失败）必告警；普通非终态失败不告警，但回件命中「超时 / 额度 / quota / 402」等短语的**非终态**失败仍会 `notify_boss()`（同单同原因 30s 去重），一轮多张超时可能刷群。豆包建议 M2 收敛为「仅终态失败告警」；M1 未改，真跑前请评估群消息量。
4. **`executor` 必须填适配器 ID**（如 `workbuddy`），不能填显示名 / label（如「WorkBuddy（构建/排查）」）。填错会 `find_adapter()` 落空 → 真跑 claim 后判「执行端未配置或未就绪」并烧掉一次机会；`--dry-run` 现在会提前报「执行端未就绪」，建议派前先跑一次。
